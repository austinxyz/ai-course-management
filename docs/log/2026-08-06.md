## nudge-email-send（归档为 2026-08-06-nudge-email-send）

用户直接问"能真发邮件吗"——`nudge`/`nudge-advanced` 一直只做到"起草文案，人工复制发送"，
这次补上"系统真的把邮件发出去"这一环。

**做了什么：**
- 详情面板新增"发送邮件"按钮（第三个动作，跟"复制文案"/"标记已催"并列），点击弹确认对话框
  显示目标邮箱，确认后走独立端点 `POST /api/nudge/send-email`
- 发送成功自动记一条 `channel=email` 的已催事件，**不经过**既有的 `_channel_for()` 微信对齐
  自动判定——不管这个学员平时走哪个渠道，走这个按钮发出去的都是邮件
- 发送失败就地报错，不落库（先发送、成功才写 DB）

**opsx 走了完整四阶段**：explore（澄清"发送邮件"是新按钮不是合并进"标记已催"、确认框、
主题固定格式）→ propose → apply（2 组 task，两组评审 99/80、98/80）→ 上线后生产实测踩坑，
加 group 3 修订（评审 99/80）→ archive。

**上线当天就踩了一个真实生产坑：**
最初选型是 SMTP + Gmail 应用专用密码（`austin.aicourse@gmail.com`），本地/CI 测试全程 mock
掉 `smtplib`，全绿。部署到 Render 后用临时测试学员（自己的邮箱）端到端一测，直接
`[Errno 101] Network is unreachable`——Render 免费档对出站 SMTP 端口（587/465/25）有平台级
封锁，跟密码对不对无关，换账号密码都无解。

**改用 Resend（HTTPS API 邮件服务）解决**：走 443 端口，不受这条封锁影响。`email_client.py`
的对外函数签名（`send_email(to, subject, body) -> None`，失败抛 `EmailSendError`）没变，
只重写了内部实现——调用方 `nudge.py` 完全不用动，这条边界划对了让切换成本降到最低。发件
域名 `austinxyz.ai` 在 Resend 后台做了 DNS 验证，发件地址固定 `noreply@austinxyz.ai`。

**已记进 CLAUDE.md Pitfalls**：Render 免费档封锁出站 SMTP 端口，要在这类免费 PaaS 上发邮件，
默认假设 SMTP 走不通，直接选 HTTP API 型发信服务，不要等部署了才发现。

**验证方式**：生产环境建一个临时测试学员（邮箱指向讲师本人），跑一次真实的
`POST /api/nudge/send-email`，确认 201 + 真的收到邮件，验证完立刻归档（软删）这个测试学员，
不留在真实名单里。

**验收标准**：backend 20+ 项（含 SMTP→Resend 切换后的重写用例）+ frontend 28 项全绿，三组
evaluator 评审全部一次通过（99/80、98/80、99/80）；生产环境真实发信验证通过。
