## nudge：MVP 上线，四组评审两次被打回都抓到真问题（96/80、100/80、98.4/70 二次过、96/80）

`docs/requirements.md` §4.4 写的催作业全链路（算名单→起草文案→发邮件→回写记录）一直没做。
这次先做 MVP：**不接真实发信通道**（不接 Gmail、不接微信自动发送），系统只算名单、起草文案、
记讲师的"标记已催"/"跳过"动作。名单判据直接复用 `homework.py` 的 `merge_states`/`state_of`，
不重新发明"谁该催"；逾期天数以所报场次上课日期为基准；同一学员同一门课多条未交报课记录只
算一条，取最早日期。新表 `nudge_events`（学员+课程+事件类型+渠道+备注+时间）是"互动记录"
能力的最小子集，字段设计上留了扩展口子但这次不建人工录入、参与度导入两个来源的入口。

四组评审两次都不是走过场：

- **group 3（前端名单+详情面板）第一次评审 80/70 被打回**：详情面板缺渠道徽章、"上次催促"
  列缺备注、渠道显示成英文 `wechat`/`email` 没本地化——三处都是"跟 mock 比对"这个动作本身
  能抓出来的问题，测试没测到是因为测试断言的是数据而不是文案。修完二次评审 98.4/70。
- **group 4（写入动作）RED 测试当场抓到一个真 bug**：草稿编辑状态最初提到父组件存成
  `Record<email, text>`，导致"选中另一人再选回来"看到的是上次编辑过的文字，违反 spec
  "编辑只影响当次展示"。RED 测试一写就复现，改法是把状态挪进按 `key={studentEmail}`
  挂载的 `DetailPanel` 自己身上，换人时组件重新挂载天然复位，不用手写重置逻辑。两条都
  补进了 pitfalls（一条讲"prop 换了但组件没重新挂载"这件事两个方向都能中招）。

## 生产 Supabase Advisor 报 `enrollments` 无 RLS 保护

查下来是虚惊但也不是——仓库代码从没用过 `supabase-js`/anon key/PostgREST，浏览器只经
Next.js 转发到 FastAPI，从不直连 Supabase 的自动 REST API。但那条自动 API **默认是开着的**，
代码不用它 ≠ 关掉了它。真正的关法在 Supabase Dashboard → Settings → Data API，已经关掉。
补进 pitfalls：这条项目一直写着"不使用其自动生成的 REST API"，但那是应用层的选择，不是
基础设施层的开关状态，两者容易被读成一回事。
