# 2026-08-02（PT）

## homework-reply-status：apply 两组一次过（99.6/80、100/70），上线当天一次生产反馈即修

讲师问"能不能把回复状态标成已回复"，聊出来才发现 `reply_status` 是纯镜像字段——
每次重新导入整列覆盖，讲师实际回复往往发生在系统之外，源文件那列常常没跟上。
新增独立的 `replied`/`replied_at` 字段与一对动作式端点（`POST .../reply` /
`.../unreply`，参照 `Student.archive`/`restore` 先例：无请求体，时间戳服务端盖），
「待回复」筛选判据从看 `reply_status` 改成看 `replied`。

apply 中途发现一处计划错误：propose 阶段写的任务是"后端 `GET /api/homework` 的
「待回复」判据要改"，但实际打开 `HomeworkClient.tsx` 才发现这个判据**从来不在后端**——
`list_homework` 只吐原始字段，筛选是前端 `awaitingReply()` 算的。按原计划写下去
会给后端加一段没人调用的逻辑，还测不出错。当场改了 tasks.md，把这两条任务的范围
收窄成"后端只负责透传 `submission_id`/`replied`/`replied_at` 三个字段"，判据判断
的活儿留给 group 2 的前端任务。已补进 `CLAUDE.md` pitfalls：写 tasks.md 前先读实现，
"这个判断在哪一层算"不能靠 spec 措辞猜。

## 上线即撞：名单表格显示旧信号，用户读成"标记没生效"

功能一上线，讲师就反馈"改变状态后，课程列表中状态没变"。查下来是设计如此——
名单表格「回复」列一直显示 `reply_status` 原文，讲师标记刻意不碰这一列（避免
下次导入把标记冲掉）。但这不是好设计：两个信号互不冲突，不代表用户分得清
哪个信号绑在哪个控件上——界面上只要还留着一处显示旧信号，新动作在那儿就是
"看不见的生效"。改成**新信号更可信时优先显示新信号**：已标记就显示「已回复」，
不再显示可能过期的源文件原文；原文退到详情面板，仅供溯源。TDD 补测、更新
spec 的 Scenario，同一个 PR 里修完（`9f71446`）。这条也补进了 pitfalls。

## homework-rubric：apply 三组全一次过（100/99/99），复用了一份搁置过的旧设计稿

`homework` spec 上线时明确写了「不显示各分项满分」，理由是满分不在 `grades.csv`
里（在另一个仓库的 `rubric.md`，两份文件对过错，不可信）——这条限制当时就说好了
"暂缓，另开 `homework-rubric` 处理"。这次把暂缓的三件事一次做掉：分项 `X/满分`、
条形图、总分按比例着色进度条，外加当时没提过的第四件——名单表格的迷你竖条。

满分给了一张新表 `homework_rubric_items`（`course_id, item` 主键，`max_score`
带 `CHECK (max_score > 0)`），讲师在课程页维护；分项名字系统自动从已导入成绩里
去重列出，不用手打，避免配错名字对不上源文件的列。`GET /api/homework` 有一条
既有硬约束——单次数据库往返——满分表用 `func.jsonb_object_agg` 标量子查询嵌进
主 `select()`，不新增 `session.exec` 调用；专门补了一条往返计数测试钉死这一点
（`test_query_roundtrips.py`）。

explore 阶段中途发现：早在 2026-07-31 那份从 Claude design 导入的稿子
（`2026-07-31-course-enrollment-design.dc.html`）里，满分展示的完整视觉设计
其实已经画过了——分项条按比例染色、总分数字染色、**名单表格每行一串迷你竖条**——
只是当时因为满分数据源没定，被 2026-07-31 那天的用户决定"暂缓"。这次直接复用
那份稿子的布局（迷你竖条、分项染色），只把三档阈值从旧稿的 85/60 换成这次重新
定的 90/70，总分额外加了旧稿没画的进度条（旧稿总分只染色不画条）。requirements
文档因此改了一版，多花了一轮 Q&A，但省了重新设计视觉的功夫。
