# course-list-order Requirements

来源：课程导入完成后讲师试用，指出两处 —— 课程列表变成了上下堆叠（设计稿是左右），
以及课程顺序应当按"第一次开课时间"倒序而不是按名字。

## 为什么

**布局是我的实现漂移。** 设计稿里课程页是左右两栏：左栏固定 `264px`、`border-right`、
浅底、独立滚动；右侧详情 `flex:1` 独立滚动（见
`docs/superpowers/specs/mocks/2026-07-29-course-enrollment-design.dc.html` 第 444 行）。
我实现成了课程 chip 横排在上、详情在下 —— 四门课时勉强能看，课程一多就会换行堆叠，
把详情越推越低。

**排序是一条从未被写下的规则。** `course-catalog` 的 spec 里没有任何关于课程顺序的条款，
这是当时明确留白的（该 spec 的起草说明原话：「没有规定课程排序……若你希望固定，说一声」）。
现在讲师说了：**按第一次开课时间倒序，最新的在前**。按名字排对他没有意义 ——
他找的是"最近在上的那门"。

## Goals

- 课程列表回到设计稿的**左右布局**：左栏固定宽度、独立滚动；课程增多时不挤压详情
- 课程按**第一次开课时间倒序**排列（最新在前）
- 顺序是**后端契约**，不是前端偏好 —— 它是数据的属性，任何客户端看到的顺序都相同

## Non-Goals

- **不改学员名单的排序** —— 那是 `student-roster`，另一条线。见下方「遗留」
- **不做手动排序 / 拖拽** —— 顺序由数据推出，不由人摆
- **不做课程搜索、筛选、分页** —— 课程是个位数
- **不改场次内部的排序** —— 场次仍按上课日期升序（先发生的在上），与课程相反是有意的：
  课程列表回答"最近在上什么"，场次列表回答"这门课怎么走过来的"
- **不把布局写进 spec** —— 视觉基准是设计稿，spec 不描述像素

## Constraints

- 架构纪律不变：排序在后端完成并体现在 `GET /api/courses` 的返回顺序里；
  前端不重新排序（前端排序会让"顺序"变成每个客户端各自的看法）
- **排序键是该课程最早一场的 `local_date`**。一门课有多场时用最早那场 ——
  "这门课什么时候开的"指第一场，不是最后一场
- **顺序必须稳定**：日期相同时以课程名、再以 id 兜底。没有兜底的排序会在每次写入后抖动
  （学员名单踩过这个坑：没有 `ORDER BY` 时 `UPDATE` 把行写到堆尾）
- 左栏宽度与边框取设计稿的值；**不新增设计元素**，本 change 只是把已有内容摆回原位

## Success Criteria

1. 三门课的第一场分别在 5 月、6 月、7 月时，列表顺序为 7 月、6 月、5 月
2. 一门课有 5 月与 12 月两场时，它按 **5 月**参与排序（用最早那场）
3. 还没有排课的课程出现在**最前**
4. 日期相同的两门课顺序稳定 —— 反复请求、以及在其中一门被编辑之后，相对顺序不变
5. 课程页为左右两栏：左栏固定宽度且可独立滚动，右侧详情独立滚动；
   课程数量增加时左栏内部滚动，**详情区不被向下挤压**
6. 前后端测试套件无回归

**生产验收**：

7. 生产上四门课按 S4（7/26）→ S3（7/19）→ S2（7/12）→ S1（6/28）排列
8. 页面为左右布局，与设计稿一致

## User Stories

- 作为讲师，我打开课程页想看到**最近在上的那门**排在最前，而不是名字碰巧排前面的那门
- 作为讲师，我的课会越来越多；我希望课程列表在左边自己滚动，而不是把详情越挤越靠下

## 已确认（2026-07-30 人工 review）

- **还没排课的课程排在最前** —— 经确认。理由：它是刚建出来、正在张罗的一门，
  沉到底部等于把最需要动手的东西藏起来
- **排序在应用层做，不在 SQL 里做**。键是子集合的聚合值（`min(local_date)`），
  而课程只有个位数；一次 SQL 聚合 join 换不来什么，可读性反而差。
  若将来课程上百，再换成 SQL
- **场次仍按日期升序**（与课程相反）。理由写在 Non-Goals 里
