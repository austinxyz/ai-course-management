# enrollment-core Requirements

报课能力的**数据主干**（`docs/requirements.md` §4.2 的第一片）：一条报课记录把学员与课程连起来，
可以指明上哪一场，能手工补录，能在学员详情与课程页两处看到。

**批量导入不在本切片内**（报课页、CSV/粘贴解析、待处理队列归 `enrollment-import`）。

## 为什么

`student-roster` 与 `course-catalog` 两条能力已上线，但**互不相干** —— 系统里没有任何东西
把"这个人"和"这门课"连起来。于是：

- 课程页的场次卡片上**不显示**「已报 N 人」（能力清单里写明了是「不显示」而不是「显示 0」——
  没有报课表时，0 是一个谎）
- 学员详情里没有报课区块
- 催作业（§4.4，核心工作流）无从谈起：它要回答"这门课谁没交作业"，
  而"这门课有谁"正是报课记录

还有一笔到期的账：**场次目前是硬删除**。`course-catalog` 归档时记下"现在没有报课表所以无害，
有了之后删掉一场会让报课记录指向不存在的场次"。本切片必须一并了结。

## Goals

- 一张报课表：学员（邮箱）× 课程 × 可空的场次，带报课日期、状态、备注、来源
- 学员详情里能看到该学员的报课记录，并能**手工补录**一条
- 课程页的场次卡片显示「已报 N 人」
- 删除有报课记录的场次被**拒绝**，并说清有几条挡着
- 状态设计成**不会腐烂**：只存需要人决定的部分，其余派生

## Non-Goals

- **批量导入**（CSV / 粘贴 / API）、报课总表页、待处理队列 —— 归 `enrollment-import`
- **API 拉取适配器** —— 阻塞于 EliteCoach101 是否开放接口（设计稿已标"待确认"）
- **作业与催作业**（§4.3 / §4.4）—— 另外的能力，本切片只为它们准备好口径
- **出勤记录**（来没来）—— 系统不跟踪，见下方「状态」一节
- **退款、收费、名额上限** —— 目前不收重复听课的费用，也不设名额
- **课程删除** —— 课程本来就没有删除入口（下线走 `offline`）

## Constraints

### 挂载：报课挂课程，场次是可空字段

设计稿（`docs/superpowers/specs/mocks/2026-07-29-course-enrollment-design.dc.html` 第 26 行）：
「报课 增加「上哪一场」——挂到场次，不只挂课程」。样本数据里 `sun.bo` 那条 `session: ""`
即"平台没给场次，需要确认上哪一场"。

挂课程而非挂场次的理由：换场次时**报课记录本身不变**（改一个字段），
"他什么时候报的名"不会丢；且能表达"报了但还没定哪一场"。

### 引用：存外键，不存名字

报课记录 SHALL 以 `students.email`（学员表主键）与 `courses.id` 外键引用，
场次为 `course_sessions.id` 可空外键。**不存课程名。**

设计稿的字段契约里写的是 `course_name`（"平台课程名原样保留，本系统做别名映射"）——
那是**导入格式**的字段，不是表结构。别名匹配 → `course_id` 的解析发生在导入层（切片 2），
落库时已经是外键。存名字会让改课程名把历史报课改坏，而课程名是明确可改的
（`course-catalog`：「课程名与简称都可改」）。

学员用邮箱而非独立 id：邮箱本来就是学员表主键（CLAUDE.md：邮箱是唯一主键）。
学员没有删除入口（只有归档），所以外键不会悬空。

### 状态：只存需要人决定的，其余派生

存库两值（英文，沿用课程场次那次定的口径）：

| 存储 | 含义 |
|---|---|
| `enrolled` | 报了名 |
| `withdrawn` | 退课 |

「已完成」**不入库**，读取时由所属场次派生：

```
无场次            → 报名
场次未到          → 报名
场次已上          → 已完成
场次已取消        → 报名     （课没上成，人还欠一场）
状态为 withdrawn  → 退课     （压倒一切派生）
```

理由：没有人会在每次课后回来把十几条记录挨个改成"已完成" —— **存下来的状态会腐烂，
派生的不会**。这与 `course-catalog` 里场次状态的做法一致（`state_override` 为空即跟随日期）。

**不设 `status_override`。** 探索时考虑过（三值覆盖），放弃的原因是它让"这个人属于哪一场"
出现两个互相矛盾的答案：场次指向已上的那一场、状态却被压成"报名"，那么「已报 N 人」
该不该算他？没有正确答案。而它想解决的场景不需要它 —— 见下条。

### 补课与重听：改场次，不改状态

- **没上成，要补后面那一场** → 把场次改到后面那场，派生状态自动回到「报名」
- **还没定补哪一场** → 清空场次，同样自动是「报名」，且落进"未定场次"这一类，正是需要跟进的状态
- **想再听一遍**（真实发生过，目前不额外收费也不阻止）→ 场次不同，天然是**第二条**报课记录，
  两条各自跟随自己那一场派生

### 唯一键：(邮箱, 课程, 场次)，另加 partial unique index

设计稿：「同一 (邮箱 + 课程 + 期次) 视为同一条报课」。重听同一门课因为场次不同，不冲突。

**Postgres 里 `NULL != NULL`**，所以普通唯一索引挡不住两条都是"未定场次"的行 ——
批量导入时每导一次就多一条。需要一条 partial unique index：
同一 (邮箱, 课程) 下**最多一条**未定场次的记录。

### 作业是一份 —— 报课记录不能直接当催作业依据

一个人重复上同一门课时有两条报课，但**作业只算一份**。
因此催作业名单 SHALL 按邮箱去重，不得逐条报课记录发送。

这条现在写下来，是因为等作业/催作业能力落地时，"把报课记录拉出来逐条发"
是最自然也最错的写法，而它的症状是**同一个人被催两遍**——用户会看到，我们不会。

### 删除场次：有报课就拒绝

有任何报课记录指向该场次时，删除 SHALL 被拒绝，并告知有几条挡着。
**退课的记录同样挡着** —— 它仍是一条指向该场次的历史记录。

不做"删除时自动把报课的场次置空"：那会**静默**把 8 个人推进待跟进状态，
而讲师不会知道自己制造了 8 条待办。删场次牵动的是真人的位子，值得多一步。

（"把这些人批量改派到另一场"是更顺手的做法，但那是一个新的写入面，留给后续切片。）

### 删除报课 ≠ 退课

设计稿里两个动作都有（状态改「退课」、以及「删除这条报课」按钮，第 1063 行）。二者语义不同，
都要保留：

- **退课** = 这件事发生过，他报了名又退了。记录留下，不计入「已报 N 人」，仍挡住场次删除
- **删除** = 这条记录本身是错的（补录时选错了人 / 课 / 场次）。记录消失，像没发生过

判据是「用户正常操作会不会撞到」：录错是常事。没有删除入口就只能留一条假的退课记录，
而那会让「退课」这个词失去意义 —— 名单上会混进一批根本没报过名的人。

（学员与课程都没有删除入口，报课有，因为它是**关系**而不是实体：关系可以是错连的。）

### 归档学员不影响报课计数

归档说的是"这个人还在不在我的名单里"，报课说的是"他报没报这门课" —— 两件事。
人真的不来了，正确的表达是把那条报课标**退课**，而「已报 N 人」本来就排除退课。

反过来做（归档即排除计数）会让**历史数字随今天的操作改写**："6 月那场当时 12 人"
在归档一个人之后变成 11。这与学员名单堆顺序那个坑是同一形状：让数字记录操作时间，
而不是数据本身。

代价：归档一个还挂着"报名中"报课的人时，那一场仍算他。所以归档确认里的
"他的 N 条报课"不只是提示，而是在问要不要顺手退课。

### 来源与报课日期

- `source` 存英文 `manual` / `platform`，界面显示「手工补录」/「平台同步」。
  本切片只会产生 `manual`（导入是切片 2），但列现在就建 —— 切片 2 不该改表结构
- `enrolled_at` 为日期（非时间戳），**必填**；手工补录时默认今天，可改。
  设计稿的规则是「ISO 日期；平台只给月份时补 01」，该规则属于导入层，本切片只要求它是个日期

### 其它

- 「已报 N 人」= 该 (课程, 场次) 的报课记录中**状态 ≠ 退课**的条数（设计稿规则）
- **退课可以改回报名** —— 标错了要能撤销，与场次状态一样是可逆的编辑
- 新建报课时**不列出已下线的课程**；既有报课照常显示（下线是"不再招生"，不是"没发生过"）
- 报课页那个 tab 在本切片**仍是占位页**，补录入口在学员详情
- 架构纪律不变：浏览器 → Next.js → FastAPI → Postgres；migration 只在 `supabase/migrations/*.sql`
- 隐私：测试数据一律虚构姓名 + `@example.com`

## Success Criteria

1. 一条报课记录可以只挂课程不挂场次；也可以指明场次
2. 场次已上时该报课显示「已完成」，且**数据库里没有存过这个状态**
3. 把报课的场次改到未来那一场，状态自动变回「报名」；清空场次亦然
4. 同一人同一门课的两条报课（场次不同）都能建出来，各自派生状态
5. 同一人同一门课**第二条未定场次**的记录被拒绝（partial unique index）
6. 标记退课后，该场次的「已报 N 人」减一；归档该学员则**不减**
7. 删除有报课的场次返回 409 并告知条数；退课的记录同样挡住删除
8. 学员详情能看到报课记录并能补录一条；课程页场次卡片显示「已报 N 人」
9. 前后端测试套件无回归

**生产验收**：

10. 给一名真实学员补录一条报课，学员详情与课程页两处的数字一致
11. 尝试删除有报课的场次被拒绝且提示条数正确

## User Stories

- 作为讲师，我想知道**这门课这一场有谁** —— 现在系统里查不到，只能翻平台后台
- 作为讲师，有人平台漏记或线下转账，我想直接补录一条报课
- 作为讲师，有人这次没上想补后面那一场，我想改一下就行，不要删了重建把报名时间丢掉
- 作为讲师，有人想再听一遍加深印象，系统要能记下她占了两场的位子，但**别催她交两次作业**

## Open Questions

（无阻塞项。以下为 2026-07-30 人工确认的边界：）

- 报课挂课程、场次可空（设计稿已定，本次确认）
- 状态只存 `enrolled`/`withdrawn`，「已完成」派生；**不设状态覆盖**
- 重听同一门课 = 两条报课；**作业仍是一份**，催作业按邮箱去重
- 删除有报课的场次一律拒绝（含退课记录）

**留给 apply 阶段实测、不得默认成立的一点**：

- partial unique index 在 `session_id is null` 上的行为要用**真实重复插入**验证，
  不能只看 migration 跑通 —— `NULL != NULL` 正是那种"索引建了但没挡住"的静默失败

`docs/superpowers/specs/mocks/2026-07-29-course-enrollment-design.dc.html`：

以及课程页场次卡片上的 `{{ s.enrolled }}`（第 511 行）。
**本切片不新增设计元素**，只是把稿子里已有的这三处做出来。

propose 阶段的 mocks 产物写成导览：标明这三处的位置与文案、
「已报 N 人」的计数规则（排除退课、不排除归档）、以及删除场次被拒绝时错误信息显示在哪。
