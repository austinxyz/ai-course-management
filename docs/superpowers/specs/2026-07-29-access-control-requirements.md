# access-control Requirements

## Goals

- 关掉当前的公网裸奔：前端页面、后端 API、以及 API 自动文档，未经授权一律不可访问
- 前端用 HTTP Basic Auth（共享密码）挡人；后端用共享 secret header 确保只有自家 Next.js 能调
- 认证逻辑**无环境分支**——本地与生产行为完全一致，消除"环境判断失误导致认证静默失效"这一整类风险
- 补上 `openspec/config.yaml` 泄露检查的盲区，让新增的认证类变量也在 `NEXT_PUBLIC_` 扫描范围内

## Non-Goals

- **不做每人一个身份** —— 讲师与合作伙伴共用同一个密码。因此无法单独吊销某一人、也无法在互动记录里区分是谁录的（CLAUDE.md 认证章节已定"不做多用户隔离"）
- **不做限流 / 防暴力破解** —— 明确不纳入本 change（依赖"密码本身足够长"这一前提，见 Constraints）
- **不做学员端登录** —— 学员不访问本系统
- **不在本 change 解除"禁止导入真实学员数据"护栏** —— 见 Open Questions 的说明
- 不做登出功能 —— Basic Auth 无此概念，要退出需清浏览器凭据
- 不引入 Supabase Auth、OAuth、magic link 等任何外部身份服务

## Constraints

- **配置缺失时必须 fail-closed。** 密码 / secret 环境变量未设置时，行为必须是**拒绝全部请求**，不得是放行。
  典型写错方式：`if (password && provided !== password) deny()` —— 变量未设时谁都能进。
  这类失败比数据库连不上更危险：DB 失败会 500 当场暴露，认证静默失效**没有任何征兆**，页面照常打开，
  可能数月无人察觉。缺配置时"谁都进不来"，第一次访问就会撞上，立刻知道。
- **认证代码中不得出现环境判断**（`NODE_ENV === 'development'` 之类）。本地与生产走同一条路径。
- **前端密码与后端 secret 必须是两个不同的值**。用途、轮换频率、泄露后果均不同；同值意味着人知道机器密钥。
- 后端 secret 走 server-side only 环境变量，**绝不可加 `NEXT_PUBLIC_` 前缀**（同 `BACKEND_URL` 既有纪律）。
- 架构纪律不变：浏览器只与 Next.js 通信。后端 secret 由 Next.js 服务端注入请求头，浏览器不可见。
- 保护范围是**整站**，middleware 默认全拦、显式放行例外。不采用"逐个路由加保护"的白名单式写法——
  那种写法在新增页面时最容易漏。
- **静态资源（`_next/static/*` 等）排除在 middleware 之外。** 泄露的是前端 bundle 的代码与页面结构，
  不含任何学员数据；而 Basic Auth 通过后浏览器会对同源全部请求携带凭据，实际差别很小。
  拿"前端代码结构可见"换掉每个静态文件都过认证的开销，这个取舍成立。
- **后端 secret 校验默认覆盖所有路由**，需放行的显式列出。与前端"默认全拦"同一原则、同一理由：
  以后新增健康检查、webhook 等路由时不会漏掉保护。
- 密码强度由人保证：不做限流意味着"够长"是唯一防线，不得使用短口令或字典词。

## Success Criteria

1. 未带凭据访问生产环境任意页面（含 `/students`、`/style-guide`、`/`）→ 返回 401，**且响应体不含任何学员数据**
   （不可"先渲染再跳转"，那样 HTML 里已经带了数据）
2. 带正确凭据访问 → 一切照常，学员名单、详情面板、错误态/加载态行为与本 change 之前一致
3. 未带 secret header 直接 `curl` 生产后端 `/api/students` → 401（而非 200）
4. 生产环境 `/docs` 与 `/openapi.json` → 404
5. 本地开发**设了密码变量时**的行为与生产完全一致（同一条代码路径，无环境分支）
6. 密码 / secret 环境变量**缺失时全部请求被拒**（fail-closed 验证；这是与 #5 不同的一条：#5 验一致性，#6 验缺配置时的方向）
7. `openspec/config.yaml` 的泄露检查已覆盖新增认证变量名
8. 前后端测试套件无回归

## User Stories

- 作为讲师，我想让这个存着真实学员联系方式的系统不再对全世界敞开，只有知道密码的人能进
- 作为合作伙伴，我想在自己的电脑上输一次密码就能用，手机上偶尔查看也能进得去
- 作为 developer，我想认证逻辑简单到没有可以写错的地方，且本地跑起来跟线上是同一套行为

## Open Questions

（无阻塞性问题。以下两条是已明确排除、但需记录的后续事项：）

- **护栏解除的时机** —— 本 change 上线后，CLAUDE.md 与 README 中"访问控制落地前不得导入真实学员数据"
  的警告仍会留在原处。这是**有意为之**：护栏继续有效，直到真要导数据时再单独、明确地解除，
  而不是随本 change 自动失效。风险是这些警告会变陈旧、进而被无视——因此在此显式记录，
  作为"导入真实数据"那次动作的前置检查项。
- **限流** —— 未纳入本 change。若将来密码可能被更多人知道、或系统暴露面扩大，需重新评估。

## 已知代价（有意接受，不在本 change 解决）

- **后端 secret 配错时，前端错误文案会指向错误的方向。** `deployment` change 的 `error.tsx` 写的是
  "服务器可能正在唤醒——免费套餐休眠后，首次访问约需 1 分钟"。本 change 之后，secret 配错会让后端返回 401，
  `getStudents()` 抛错，落到同一个错误页——于是页面在说"服务器在唤醒"，而真实原因是密钥配错了，
  排查方向被带偏。

  接受的理由与 fail-closed 一致：这是**部署时立刻撞上**的问题（第一次访问就出现），不是运行时偶发、
  可能长期潜伏的问题。区分 401 需要给错误页加一条分支，收益不足以抵掉复杂度。
  代价是排错的头几分钟可能被文案误导——在此记录，以免将来重新踩一遍。

## Referenced Capabilities

- ADD `access-control` —— 新能力。理由：访问控制是横切关注点，不属于"查学员名单"这一能力的语义；
  它的 SHALL（未授权请求应被拒绝、配置缺失应 fail-closed 等）独立成篇比塞进 `student-roster` 更清晰。
  `student-roster` 的既有对外契约不因本 change 改变。

## 待 apply 阶段实测确认

- Render 的健康检查在后端对未授权请求返回 401 时，是否仍判定服务健康
  （401 是一个正常响应，理应算"服务在跑"，但需实测而非假设）
- 移动端浏览器保存 Basic Auth 凭据后的实际体验（首次弹窗后是否真能无感）
