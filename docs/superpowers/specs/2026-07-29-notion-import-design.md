# Phase 1 Notion 学员数据导入

## 为什么

Phase 1 的学员档案存在 Notion 的「学员库」里，共 21 条。Phase 2 自建系统上线后，
Notion 方案停用（见 [CLAUDE.md](../../../CLAUDE.md) 数据来源表：「历史学员/互动 —— Notion（Phase 1）——
一次性导入后停用」）。这些记录里有人工录入的备注与标签，重建不了。

## 实际数据（2026-07-29 实测）

摸清数据之后，这件事比预想的小得多。

| | 条数 |
|---|---|
| 学员库总记录 | 21 |
| 有邮箱（可导入） | 18 |
| 无邮箱（本次不处理） | 3 —— Lily Q、Danny、达莱 |
| 有备注 | 11 |
| 有标签 | 3 |
| 有微信号 | 1（在 Danny 身上，本次导不进来） |

其中 4 条邮箱是 2026-07-29 由讲师补录进 Notion 的（Dottie Li、Jason Yang、Xin、June），
补录之前有邮箱的只有 14 条。

**互动记录库共 23 条**，其中 19 条是「作业」类型，由 `ai-course/tools/student-sync/sync_to_notion.py`
从 `grades.csv` 生成的衍生数据 —— CSV 仍在，可随时重推。剩余 4 条是 1:1（Zoom）人工记录。

### 那 3 个没有邮箱的人是谁

不是边缘人群，恰恰相反：7 个原本无邮箱的记录中，5 个是 Demo Day 讲者，2 个做过 1:1。
他们没有邮箱的原因是 **sync 脚本要求姓名与邮箱同时存在**，而 Demo Day 讲者走的是项目演示，
不经过邮件交作业那条链路 —— 于是他们从未被自动化流程建档，只能靠人工敲入。
**他们是被工具系统性漏掉的核心人群，不是无关紧要的记录。**

补录后仍缺邮箱的 3 人中，Danny 身上有全库唯一的微信号 `danny_on_the_way`。
微信号需要人工比对群名单才能获得（见 CLAUDE.md §微信昵称不可作为标识），
这条对齐结果暂时进不了系统。

### 为什么不能靠 Gmail 找回邮箱

实测 `austin.aicourse@gmail.com`：邮箱本身覆盖 Phase 1 时段（6 月有大量 Session 1/2 作业提交），
搜索功能正常，但这几个人**零命中**。

更根本的问题是这个方法本身不成立。这 3 个人在 Notion 里的名字（`Lily Q`、`Danny`、`达莱`）
是微信群显示名，而 CLAUDE.md 写明「微信昵称会变，任何按微信名找人的逻辑都是错的」。
即使 Danny 发过邮件，其邮件署名也未必是 "Danny"。
**因此「Gmail 里搜不到」只证明按昵称检索行不通，证明不了这个人没有邮箱。**

## 目标

把 18 条有邮箱的记录导入 `students` 表，使名单反映 Phase 1 的真实学员。

## 非目标

- **不改 schema。** 邮箱继续作为主键。
- **不导互动记录。** 19/23 可从 `grades.csv` 重推；余下 4 条 1:1 记录若要保存，是独立的建模工作。
- **不导** `课程`、`作业质量`、`问题活跃度`、`1:1 次数`。前两者是 CSV 的衍生数据；
  `问题活跃度` 全库为 0；`1:1 次数` 仅 4 人有值。且 CLAUDE.md 规定
  「评分维度按课程变化，新增课程不得要求修改数据库结构」—— 把分数拍平到学员表上与该约束相左。
- **不处理** Lily Q、Danny、达莱。
- **不做 opsx change。** 一次性、18 条记录、无新能力，走完整四阶段是过重的。

### 关于那三个默认值

`region`/`level`/`source` 在 API 上是必填枚举，Notion 里没有对应概念，而枚举里
**没有「未知」这个取值**。因此这三个值是讲师指定的统一默认，不是从数据推导出来的。

落库之后，它们与人工核实过的值在结构上无法区分。`Phase1导入` 标签就是为此存在的：
它让这 18 条可被整批检索出来，日后逐个核实。

标记选用标签而非追加到 `note`，是因为 `note` 装的是讲师手写的内容，
往里混机器文本会污染唯一一份不可再生的数据。

## 执行

一次性脚本，位于 `tools/notion-import/`，含独立 `requirements.txt`。

```
1. dry-run  —— 打印将创建的 18 条与冲突检测，不写任何数据
2. 人工确认
3. 实跑    —— 冲突（邮箱已存在）跳过，不覆盖
```

**跳过而非覆盖**：这与系统既有语义一致（`POST /api/students` 遇重复邮箱返回 409 且不写），
且生产库已存有 1 条真实学员记录（2026-07 那批，不在 Notion 中，已确认无冲突）。

凭据（`NOTION_API_KEY`、`BACKEND_URL`、`BACKEND_SECRET`）在运行时由讲师从自己的 shell 提供。

**脚本不含任何真实学员数据** —— 邮箱与姓名全部从 Notion 实时读取。
这是 CLAUDE.md §隐私 的硬性要求：仓库不得提交任何真实学员数据，含测试夹具。

## 验证

脚本直接写生产库，dry-run 是唯一防线，因此它必须被证明真的不写：

1. 对生产库跑 dry-run，确认输出 18 条待建、0 冲突，且生产库记录数不变
2. 指向**本地** Supabase 实跑一遍，逐字段核对映射结果（尤其是两处 `作业优秀` 与全量 `Phase1导入`）
3. 本地重跑一次，确认 18 条全部报冲突跳过、无重复记录
4. 最后才对生产实跑

## 验收标准

- 生产库学员数从 1 增至 19
- 抽查：Helen He 与 Guoqing Zhang 带 `作业优秀`，全部 18 条带 `Phase1导入`
- 11 条备注原样落库
- 重跑脚本不产生任何重复记录
