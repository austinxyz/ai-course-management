# student-write Requirements

## Goals

- 把学员名单页上已经存在、但点了不落库的写操作接通：逐字段编辑、标签增删、备注编辑、新增学员、归档/恢复
- 归档需要 schema 变更（现有 13 列里没有任何表示"已归档"的字段），本 change 一并做掉
- 写入路径经 Server Actions，浏览器不直连 FastAPI，维持既有架构纪律
- 写接口做**纵深防御**鉴权：不把整个写入面押在 `proxy.ts` 单点上

## Non-Goals

- **不做乐观更新** —— 提交后等服务器确认再更新界面
- **不做并发控制** —— 两人同时改同一条学员，后写的赢。不加版本号、不加锁、不做冲突提示
- **不做批量编辑** —— 一次改一个学员的一个字段
- **不做编辑历史 / 审计日志** —— 谁改了什么不留痕（共用一个密码，本来也区分不出人）
- **不做邮箱修改** —— 邮箱是主键且 UI 已声明"保存后不可修改"
- **不做硬删除** —— 只有归档（软删除）。UI 已声明"硬删除需超管权限"，本 change 不新增删除端点。
  后果：清理误建的记录只能直连数据库，这是有意的取舍——存的是真人联系方式，
  让界面上存在一个"永久抹除"按钮，风险大于便利
- **不做报课/作业/催作业相关的写入** —— 各自独立 change
- **不解除"禁止导入真实学员数据"护栏** —— 那仍是单独、明确的决定

## Constraints

- 架构纪律不变：浏览器只与 Next.js 通信。写操作走 Server Actions（在 Next.js 服务端执行），
  由它持 `BACKEND_SECRET` 调 FastAPI。客户端组件不得直接 fetch 后端。
- **每个 Server Action 内部必须独立校验凭据**，不得仅依赖 `proxy.ts` 覆盖。
  Next.js 文档明确警告 Server Functions "reachable via direct POST requests, not just through your
  application's UI"。失败形状比读接口严重得多：读被绕过是泄露，**写被绕过是数据被篡改**，
  而 Server Action 在服务端、手里就握着 `BACKEND_SECRET`，后端会照单全收。
  本项目已经吃过一次"框架约定改名导致文件不执行"的亏（`middleware` → `proxy`），不押注单点。
- 写接口的枚举字段（region / level / source）**用 Pydantic `Literal` 校验请求体**。
  这兑现 `student-management` 当时的决定——`Literal` 不能用在只读响应上（一行脏数据会让整个列表接口 500），
  但请求体校验正是它该在的位置。
- 邮箱为主键且不可修改；写接口不接受邮箱变更。
- 归档是**软删除**：记录与其关联数据都保留，只是不再进入在读名单。语义已由现有 UI 文案定死
  （"作业与互动记录都还在"）。
- **归档/恢复用独立端点，不作为字段更新的一部分。** 归档是一个动作而非"改一个字段"，
  且归档时间必须**由服务端盖**——让客户端提交时间戳没有任何好处，却允许它填入任意值（包括伪造的过去时间）。
  字段更新端点不接受归档字段。
- 隐私纪律不变：测试一律用虚构姓名与 `@example.com` 邮箱。

## Success Criteria

1. 逐字段编辑（微信号/微信名/微信昵称/区域/基础/来源/行业/性别/年龄）提交后落库；刷新页面仍在
2. 标签增删落库；备注编辑落库；均刷新后仍在
3. 新增学员落库，出现在名单中
4. 归档学员后其从"在读"消失、出现在"已归档"；恢复后逆向；**刷新后状态仍正确**
5. 归档不删除数据 —— 被归档学员的所有字段在恢复后与归档前一致
6. 新增时邮箱与**已归档**学员重复 → 报错提示该邮箱已归档并引导去恢复，**不自动覆盖已有记录**
7. 新增时邮箱与**在读**学员重复 → 沿用现有的"打开该学员"引导
8. 写请求带非法枚举值（如 `region: "火星"`）→ 后端拒绝
9. **未携带凭据直接 POST 到 Server Action → 被拒绝，且数据未被修改**（纵深防御的核心验收，
   必须实测而非推断）
10. 保存过程中界面显示进行中状态；保存失败时显示失败并保留用户输入，不静默丢弃
11. 前后端测试套件无回归

**生产验收**（生产库刻意为空，因此需专门安排）：

12. 在生产**新建一条明显虚构的测试记录**（`deploy-test@example.com`），走完
    新增 → 编辑一个字段 → 打标签 → 归档 → 恢复 的全链路，每一步都刷新页面确认真正落库
13. 验收结束后该测试记录必须从生产库清除，生产库回到空表。
    **注意：清除只能直连数据库执行（`DELETE FROM students WHERE email = ...`）**，
    因为硬删除不是本系统的功能——UI 明写"硬删除需超管权限"，本 change 也不新增删除端点。
    这是一次有意的、一次性的手工数据库操作
14. 使用虚构测试数据不构成对"禁止导入真实学员数据"护栏的违反 —— 护栏禁的是**真实**学员信息；
    但该记录不得残留，否则会污染后续导入真实数据时的判断

## User Stories

- 作为讲师，我在详情面板里补上某个学员的微信号后，希望它真的存下来 —— 现在刷新一下就没了，
  等于这个界面在骗人
- 作为讲师，我想给学员打标签、写备注，下次打开还在
- 作为讲师，我想把结课或退课的学员归档，让他们不再出现在催作业名单里，但不丢掉历史记录
- 作为合作伙伴，我录入一位新学员时，如果这个邮箱以前处理过，我希望系统告诉我，而不是默默新建一条
  或悄悄覆盖掉之前的记录

## 待 review 确认（我起草时自行判断，可推翻）

- **归档字段用 `archived_at timestamptz`（null = 在读）而非 boolean** —— 多存"何时归档"几乎零成本，
  且与需求文档 §4.5 互动记录的流水思路一致。若认为 YAGNI，改 boolean 亦可。
- **失败时的错误呈现位置** —— 倾向就近显示在被编辑的字段旁，而非全局提示；Phase 4 mock 定形。

## Design System

沿用既有实现（claude.ai/design 导入，见 `frontend/app/globals.css` 的 token）。
Phase 4 的风格选择跳过——设计系统已定，不是预设风格库里的条目（同前几个 change 的处理）。

**视觉 mock 照常产出**，因为这三类状态在代码里确实不存在：
`docs/superpowers/specs/mocks/2026-07-29-student-write-mocks.html`

mock 里定死的几处判断：
- **保存中只锁那一行**，不遮罩整个面板、不禁用其它字段——改一个字段等一次往返，
  锁死整块面板会让"连续补几个字段"变得难受
- **保存失败必须保留用户输入**，输入框留在编辑态、内容不回退成旧值。
  刚敲进去的微信号丢了最伤——那是需要人工对齐才拿得到的信息（requirements §5）
- **错误就近显示在字段下方**而非全局提示：全局 toast 说不清是哪个字段没存上
- **归档进行中禁用按钮并改字**，防连点导致重复请求

## Referenced Capabilities

- MODIFY `student-roster` —— 该能力目前只有读契约（列表、按邮箱查、邮箱唯一、微信号可空）。
  本 change 为其补上写契约：字段更新、新增、归档/恢复的行为，以及写入面的鉴权要求。
  读契约本身不变。
