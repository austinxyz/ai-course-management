# course-scheduling-fields Requirements

来源：2026-07-30 准备把真实课程从 [course-portal](https://austinxyz.github.io/course-portal/)
导入生产时，发现刚上线的 `course-catalog` 有两处**存不下真实数据**。
本 change 修这两处；导入本身是另一件事，见
[2026-07-30-course-import-design.md](2026-07-30-course-import-design.md)。

## 为什么

`course-catalog` 的两个字段是照设计稿的**示例值**做的，不是照真实数据做的：

1. **每场时长做成了 1/2/3/4 小时的 chip**（设计稿里那四个选项），列是 `hours int`，
   校验 `ge=1 le=4`。而四门真实课程**全都是 150 分钟** —— 2.5 小时，这个列存不下。
   不是边缘情况，是全部数据。
2. **场次时间硬编码「按美西记」**（表单标签就是 `时间（美西）`），
   而四门真实课程全部排在 **8:30 PM ET**。数据库那层没问题（`tz` 本来就是每场一个字段），
   卡住的是界面：通过 UI 建的场次一律美西，讲师要录美东的课就得自己先把 20:30 换算成 17:30 ——
   而「不用手算时区」正是这个功能存在的理由。

设计稿里其实写了「这里只管全课默认时区和时长」，但那个默认时区字段我没实现，
直接把美西写死进了 schema 默认值与表单文案。

## Goals

- **时长以分钟存储**，150 分钟能存下且界面能录入
- **课程有默认时区**，新增场次时预选它
- **新增/编辑场次可以选"我按哪个时区在想"**，标签跟着选中的时区走；
  存的仍是那个时区的墙上时间 + IANA 时区名，其它时区照旧派生
- 既有的换算正确性不回退（跨夏令时的断言仍然成立）

## Non-Goals

- **不导入课程数据** —— 那是一次性脚本的事，见上面那份 import design
- **不做价格与组合价** —— `docs/requirements.md` §2 明确「不做支付/对账」，收款在 Zelle + EliteCoach101
- **不加「期次」字段** —— 场次的「第 N 场」是按日期算出来的位置，不是存下来的编号。
  补录更早的场次会让后面的重新编号，这是**期望行为**（编号永远与时间顺序一致），
  且报课记录挂的是场次 id 不是编号，重排不动任何数据。
  2026-07-30 与讲师确认按这个走
- **不做课程删除** —— 仍然只有上架 / 已下线
- **不改场次的时区来源** —— `tz` 仍是每场自己的，课程的 `default_tz` 只作为新增时的预选值。
  改课程默认时区**不回溯**已有场次
- **不做任意时区搜索/选择器** —— 时区 chip 就是界面已有的那四个（美西/美东/加拿大/上海）。
  API 仍接受任意 IANA 名（导入脚本要用），只是界面不提供

## Constraints

- 架构纪律不变：浏览器只与 Next.js 通信；写操作走 Server Actions；只有 FastAPI 访问数据库；
  migration 只进 `supabase/migrations/*.sql`
- **`hours` 换成 `duration_minutes` 是替换而非并存**。两个来源必然有一天不一致 ——
  migration 回填 `hours * 60` 后删掉旧列
- **`duration_minutes` 校验 15–600**。0 或负数不是课；上限防手滑多打一个 0。
  不再限制成"整小时"，因为真实值就是 150
- **`courses.default_tz` 的 DB 默认值留 `America/Los_Angeles`**（中立值，与场次默认一致），
  讲师的四门课在导入时显式设为 `America/New_York`。
  DB 默认不跟着某一个用户的排课习惯走
- `default_tz` 与场次 `tz` 都用既有的 `TimezoneName` 校验器（zoneinfo 认得的键才收）——
  写错的时区名会在读取时炸在换算上，那时离写入点已经很远
- **界面上的时区 chip 与 `lib/tz.ts` 的 `ZONE_ROWS` 同一份来源**，
  否则会出现"能选、但换算行里不显示"的组合

## Success Criteria

1. 课程时长可录入 150 分钟并落库；刷新后仍是 150
2. 录入 0、负数、10000 被拒（4xx），库中值不变
3. 既有课程的 `hours` 在 migration 后变成对应的分钟数（`2` → `120`），无数据丢失
4. 课程可设默认时区；新增场次表单预选该时区，标签显示为 `时间（美东）` 这类跟随值
5. **按美东 20:30 建的一场（日期取 2026-07-31，夏令时期间）**，其美西行显示 `17:30`（同日）、
   上海行显示 `08:30 次日` —— 换算基准是场次自己的 `tz`，不是硬编码美西。
   **日期必须写死**：同样是美东 20:30，12 月那场的上海行是 `09:30 次日`（美国退出夏令时、中国不用），
   不锁日期的断言会在换季后自己变红
6. 改课程的默认时区**不改变**已有场次的显示时间
7. 跨夏令时的既有断言不回退：两场同为美西 19:30、10 月与 12 月，上海仍分别是次日 10:30 / 11:30
8. 时区名非法（`Mars/Olympus`、空串）在创建与更新两条路径都被拒
9. 前后端测试套件无回归；`supabase db reset` 后 migration 可重放

**生产验收**：

10. 生产上那门课的时长显示为分钟数且与 migration 前等价
11. 在生产按美东建一场，确认美西/上海行的换算正确（这一条与导入脚本的验收重叠，
    先跑本 change 的即可）

## User Stories

- 作为讲师，我的课是 150 分钟，我想如实填进去 —— 现在只能选整小时，填不了
- 作为讲师，我的课排在**美东**晚 8:30，我想直接这么填，而不是先在脑子里换算成美西 5:30 再填
- 作为讲师，我想让某门课记住它通常按哪个时区排，下次加场时不用重选

## Open Questions

（无阻塞项。以下为已决定项的记录：）

- **时长单位** —— 分钟，替换 `hours`（2026-07-30 确认）
- **时区选择放在哪** —— 场次表单可选 + 课程默认（同上）

## 已确认（2026-07-30 人工 review）

三处自行判断的地方经确认照做：

- **时长用数字输入而非 chip**。真实值是 150，而 90/120/150/180 这类 chip 一旦不够用
  就会退化成"选一个最接近的"——那正是这次要修的毛病。若你希望有快捷 chip，
  可以在输入框旁加几个，但输入框是主
- **`default_tz` 只影响新增时的预选**，不回溯已有场次。回溯会在改一个"默认值"时
  静默改掉历史场次的含义
- **DB 默认值留美西**（见 Constraints）。也可以改成美东，但那是把某一个用户的习惯写进 schema

## Design System

沿用既有实现。视觉基准仍是
`docs/superpowers/specs/mocks/2026-07-29-course-enrollment-design.dc.html`
的 `sc-if isCourses` 与 `showCourse` 两个分支 —— 但**本 change 有意偏离设计稿两处**，
因为设计稿给的是示例值而非真实约束：

- 「每场时长」的 1/2/3/4 小时 chip → 分钟输入
- 「时间（美西）」固定文案 → 跟随所选时区

propose 阶段的 mocks 产物写成导览（同 course-catalog 的做法），
把这两处偏离与其理由写进去，免得实现时又照着稿子抄回来。

## Referenced Capabilities

- MODIFY `course-catalog` —— 「课程可维护」的字段清单里 `每场时长` 的语义从小时改为分钟并给出取值范围；
  新增课程默认时区的要求；「场次可排，每场独立讲师」补充：录入时可指定该场的时区，
  界面标签跟随。跨时区换算与状态派生的要求不变
