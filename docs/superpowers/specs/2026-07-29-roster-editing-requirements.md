# roster-editing Requirements

来源：2026-07-29 对照 [docs/requirements.md](../../requirements.md) §4.1 逐项体检，找出四处缺口。
其中两处（标签白名单、gender/age/industry 批量导入）经确认进 backlog，本 change 只做剩下三项。

## Goals

- **姓名可编辑。** §4.1 的 8 个信息项里，姓名是唯一没有写入路径的一项。
  导入进来的名字带群昵称残留（`Xin`、`Jessie` 这类），录错只能归档重建，而重建会丢掉备注 ——
  备注是全系统最不可再生的数据
- **搜索能匹配微信昵称、微信名与微信号。** 现在只匹配姓名和邮箱，
  于是「人工肉眼对齐微信」这个 §5 指定的核心工作流在界面上没有检索入口
- **把生产词表搬出 `mock-data.ts`。** 该文件里**没有任何 mock 数据** —— `TAGS` / `TAG_COLORS` /
  `SOURCES` / `LEVELS` / `TZ_BY_REGION` / `FIELDS` / `BLANK_FORM` / `NAV` / `PAGES`
  全是线上行为与线上文案。文件名会让人（包括 agent）以为可以随便改或直接删
- **顺带删掉 `FIELDS` 里的幽灵字段 `sid`。** 详情面板渲染一行「学员 ID」，
  但 `Student` 类型里没有这个字段 —— 靠 `keyof Student | "sid"` 这个类型后门放进来的，
  取不到值。搬迁必然碰到它，留着就是把已知的坏东西搬到新家

## Non-Goals

- **不做标签自由输入** —— 标签仍是白名单。「白名单可扩 vs 自由输入」是产品选择，已确认进 backlog。
  已知后果：`Phase1导入` 这类不在白名单里的标签**筛选不出来**，
  而那个标签存在的唯一理由就是让 18 条导入记录可被整批捞出来复核 —— 这个损失是知情接受的
- **不做 gender / age / industry 的批量导入** —— 目前手工维护，等确定导入方式后另开 change
- **不做改名留痕** —— 表里没有任何时间戳，改完看不出原值，这是明确取舍。
  内部工具、共用一个密码，本来也区分不出操作者；留痕属于 §4.5 互动记录那条线
- **不做后端搜索与分页** —— 列表已全量返回，筛选在客户端。19 条记录，
  等到量级真的压不住再谈（§4.1 提到大群 117 人，仍不构成压力）
- **搜索不匹配标签与备注** —— 备注里存着大段 Demo Day 描述文案，
  把它纳入匹配会让搜索结果噪音压过信号。标签已有独立的筛选器
- **不做重名合并 / 去重** —— 需求 §5 记录了「两位 Charlie」的存在，
  但合并两条记录涉及关联数据归属，是独立问题
- **不做区域时区聚合** —— §4.1 提到区域可用来算「哪个时段覆盖最多人」，那是独立能力
- **不改邮箱可变性** —— 邮箱仍是主键、仍不可修改
- **不做 schema 变更** —— 三项都不需要新列，`supabase/migrations/` 不增文件

## Constraints

- 架构纪律不变：浏览器只与 Next.js 通信，写操作走 Server Actions，由其持 `BACKEND_SECRET`
  调 FastAPI。姓名更新复用 `PATCH /api/students/{email}` 与既有的 `updateStudentField` 通道，
  不新增端点
- **姓名的写入校验要和其它字段区别对待。** 其余可编辑字段允许清空（清空是合法编辑），
  姓名不允许：它是列表与详情面板的显示身份，也是列表排序键。空姓名会让一行变成不可辨认的空白。
  规则定死为：**先 trim，trim 后为空则拒绝**，返回 422（Pydantic validator 层，
  与 `email` 转小写同一层）
- **该校验同时作用于新增与更新两条路径。** `StudentCreate.name` 目前是裸 `str`，
  空姓名建得出来。只在 update 上拦会留一个洞：我们要防的状态照样能从新建路径产生。
  两个 schema 共用同一个姓名 validator
- **`StudentUpdate` 的哨兵语义不能被打破。** 每个字段是 `str | None = None`，`None` 表示
  「这次请求没提到它」（配合 `exclude_unset`），显式 `null` 已在边界被拒。
  新增的 `name` 字段必须落在同一套规则里，不得成为例外
- **搜索是检索辅助，不是身份匹配。** CLAUDE.md §微信昵称不可作为标识 规定
  「任何按微信名找人的逻辑都是错的」—— 那禁的是**程序化地用昵称确定身份**
  （自动 join、自动去重、自动建档）。本 change 加的是让人在界面里输入昵称片段、
  肉眼确认是谁、然后手工填微信号，正是 §5 要求的对齐入口。
  实现上不得出现任何按昵称自动关联记录的逻辑
- 搜索匹配 5 个字段：姓名、邮箱、微信昵称（`nick`）、微信名（`wxName`）、微信号（`wechat`）。
  **任一字段包含查询串即命中**，大小写不敏感，查询串两端 trim
- 列表按姓名排序（`ORDER BY name, email`）。改名会让该行在列表里移动位置 —— 这是排序生效的正常表现，
  不是 bug，但改名后选中态必须仍指向同一条记录（选中态以邮箱为键，不以行号）
- 词表搬迁**只移动、不修改内容**（删 `sid` 除外，且该删除单独一个 task）。
  搬迁与行为改动在 tasks 里分开，否则一旦出问题分不清是搬错了还是逻辑改错了

## Success Criteria

1. 详情面板可编辑姓名，提交后落库；刷新页面仍是新值
2. 提交空白姓名（空字符串或仅空格）被拒绝（422），库中姓名不变，
   界面给出失败提示并保留用户输入
3. 姓名两端空格被 trim 后落库（`"  张三  "` → `"张三"`）
4. **新增学员时姓名为空白同样被拒绝**，不产生记录
5. 姓名更新只改姓名 —— 其余字段（尤其备注、标签、微信号）不受影响
6. 更新请求体里带 `email` 仍不会改写主键（既有行为不回归）
7. 改名后列表按新姓名重新排序，且详情面板仍停留在同一条记录上
8. 搜索框输入微信昵称片段可命中对应学员；输入微信名、微信号片段同样命中；大小写不敏感
9. 搜索仍能命中姓名与邮箱（既有行为不回归）
10. 搜索**不**命中仅在备注或标签中出现的字符串
11. 代码中不存在按微信昵称自动关联/去重/建档的逻辑（人工 review 项，非自动化断言）
12. `TAGS` / `TAG_COLORS` / `SOURCES` / `LEVELS` / `TZ_BY_REGION` / `FIELDS` / `BLANK_FORM` /
    `NAV` / `PAGES` 不再从名为 `mock-data` 的模块导出；搬迁前后 UI 行为逐项一致
13. 详情面板不再出现「学员 ID」行，`keyof Student | "sid"` 类型后门随之消失
14. 前后端测试套件无回归（当前后端 34 passed）

**生产验收**：生产库现有 19 条真实记录，因此不新建测试记录，改为在既有记录上做可逆操作：

15. 挑一条**导入来的**记录（带 `Phase1导入` 标签，姓名已知有群昵称残留的那类），
    改名 → 刷新确认落库 → 改回原名 → 刷新确认。原名要先记下来，
    因为系统不留痕，改错了没有第二处可查
16. 在生产搜索框用某位学员的微信昵称片段检索，确认命中

## User Stories

- 作为讲师，我发现导入进来的某个学员名字是他的群昵称而不是真名，我想直接改掉，
  而不是归档重建、把备注一起丢掉
- 作为讲师，我拿着微信群名单逐个对齐时，我想在搜索框里敲昵称片段找到那个人，
  然后把微信号填上 —— 现在我只能靠姓名或邮箱搜，而昵称恰恰是我手上唯一有的信息
- 作为讲师，我想知道某个微信号是谁，搜一下就出来

## Open Questions

（无阻塞性问题。以下为已排除项的记录：）

- **改名留痕** —— 明确不做，见 Non-Goals
- **姓名长度上限 / 字符校验** —— 除「trim 后非空」外不加限制。真名的形态无法预设，
  过度校验会拦住合法姓名

## 已确认决定（2026-07-29 review）

- **空姓名在 Pydantic validator 层拒绝，不加 DB CHECK 约束。** 理由与 pitfalls 里那条一致：
  DB 层加约束会让未来的格式演进变僵，且本系统没有绕过 API 直写的路径
- **create 与 update 共用同一个姓名 validator**（见 Constraints）
- **删掉 `sid` 幽灵行**，而不是改成显示邮箱 —— 详情面板顶部已展示邮箱，
  再加一行只是重复
- **搬迁目标 `frontend/app/students/vocab.ts`**，`BLANK_FORM` 一并搬（它引用枚举默认值）。
  不叫 `constants.ts` —— 那个名字会吸引一切杂物
- **`TZ_BY_REGION` 在前后端各有一份**（`frontend/app/students/vocab.ts` 与
  `backend/app/schemas.py`），本 change **不统一** —— 跨语言共享枚举需要生成机制，
  是独立决定。但搬迁时要留一行注释指明这处重复，否则下一个人改了一边不改另一边

## Design System

沿用既有实现（`frontend/app/globals.css` 的 token），**不产出视觉 mock**，
因此 `HAS_UI_SURFACE: no`。

这个标记值得解释：本 change 确实改动界面，但**没有任何新的视觉状态**。
姓名走详情面板既有的「字段行 + 就地编辑 + 保存中/失败态」模式 —— 那套状态由 `student-write`
的 mock 定形并已实现，姓名只是多一行；搜索是既有输入框的匹配范围变化，无视觉差异；
词表搬迁与删 `sid` 行更没有。给这种改动画 mock 只会产出一张与现状雷同的图。

唯一有产品含量的视觉决定是**搜索框的 placeholder 文案** —— 它是用户知道「能搜昵称」的唯一途径。
定为：`搜索姓名 / 邮箱 / 微信`。不在 mock 里定，在实现时直接落这一版。
