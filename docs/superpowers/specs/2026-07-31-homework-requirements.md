# homework Requirements

把 `grades.csv` 里已经批完的作业成绩变成系统里可查的一页，并且让「谁报了课但没交」这个
判断第一次有地方可算。

**不是**催作业（§4.4）。名单算出来之后的起草文案、发邮件、回写互动记录，全部归下一个 change。

## 为什么

作业数据是这套系统里**唯一已经完整存在、却完全没进库**的一块。`enrollment-backfill`
刚刚证明了它的价值 —— 30 条报课记录里绝大多数是从这些成绩倒推出来的。但倒推只用了
「有没有成绩」这一个比特，成绩本身（总分、10 个分项、亮点、改进建议、回复状态）全丢了。

同时 §4.4 催作业的核心判据是「**有报课记录但无提交记录**」。这个判断今天在系统里
**根本算不出来** —— 因为提交记录不在库里。作业这一页是催作业的前置条件，不是并列功能。

## 数据现状（2026-07-31 实测）

权威源：`ai-course/tools/homework-grader/session*/grades.csv`。共 **28 行 / 27 人**真实提交
（`session1` 有一人对同一门课交了两次）。

列的形状各表一致：`姓名, 邮件, 提交时间, 总分, <各分项…>, 亮点, 改进建议, 回复状态`。

```
session1/  18 行  A1工作流结构 A2数据传递 A3Cowork特性 B1提示词三要素 B2输出路径
                  B3可复现性 C1输出真实性 C2输出匹配度 D1心得字数 D2心得深度      10 项
session2/   9 行  E1领域与结构 E2Wiki数量 E3Wiki结构 E4Wiki质量 E5专业洞察
                  F1PPT提交 F2PPT质量 G1心得字数 G2心得深度                       9 项
session3/   1 行  K1网站上线 K2领域与Brief K3内容真实性 K4设计质量 L1截图完整性
                  M1心得字数 M2心得深度 N1海报 N2PPT                              9 项
session4/   0 行  与 session3 同形，submissions/ 也是空的                         —
```

分项列**各课之间零交集**。这正是 CLAUDE.md 那条硬约束的来源：新增课程不得要求改表结构。

### 目录名不可信 —— 已经错了一处

`session3/` 与 `session4/` 的 `references/rubric.md` 是**对调的**：

| 文件 | 内容 | 实际属于 |
|---|---|---|
| `session3/grades.csv` + `submissions/` | 建站 · 海报 · PPT | S3「从一句话到成品」✅ 目录名对 |
| `session3/references/rubric.md` | `/market-daily` Skill 三层工程 | **S4「AI 炒股分析系统」** ❌ |
| `session4/references/rubric.md` | Claude Design 建站 | **S3** ❌（文件里还写着「本课线上排期显示为 Session 3」） |
| `session4/grades.csv` | 0 行，表头是 S3 的形状 | S3 的空壳 |
| `session4/submissions/` | 空 | — |

**S4 一份提交都没有。** `enrollment-backfill` 当时存疑的 `session4 → S4` 映射，
现在有了结论：那条映射不成立，`session4/` 整个目录是 S3 的残留。

### 两处数据不自洽，镜像必须如实反映

- `session2/grades.csv` 有 **1 行「总分 ≠ 分项之和」**。所以总分**必须原样存 csv 里那个数**，
  不能现算 —— 现算会与源文件悄悄不一致，而这一页的全部价值就是"忠实反映源文件"。
- 各分项的**满分不在 csv 里**，在 `rubric.md` 里（而那两份还是错位的）。因此本次不做满分。

## Goals

- `grades.csv` 的内容进本系统数据库，**新增课程不需要改表结构**
- 作业页 `/homework`：按课程看名单，每人一个状态，能看到某人这门课的完整评分
- 「有报课记录但无提交记录」第一次可计算 —— 为 §4.4 打底
- 同步是可重复的：同一份 csv 跑两遍，结果一致，不产生重复行

## Non-Goals

- **催作业（§4.4）全链路** —— 起草文案、发邮件、回写互动记录、已催次数。下一个 change
- **在网页上触发同步。** `grades.csv` 在另一个仓库，Render 上的后端看不到那些文件；
  CLAUDE.md 明令跨仓库数据先导入、不做运行时跨仓库依赖。同步只能是**本地 CLI**
- **任何写入接口。** 这一页全只读（见下方「真相归属」）
- **各分项满分、分数条形图、`11/15` 这种写法** —— 满分不在 csv 里
- **历史版本**（覆盖前留旧值、「第 2 次提交 +6 分」）
- **「截止后交 / 按时交」标记** —— 需要给 courses 加「作业截止日期」列并人工填四门课。
  截止日期对 §4.4（「已过 N 天」）有用，跟着那个 change 一起加更合适
- **作业原文与批改报告**（`submissions/*.md`、`*_report.md`）—— 只导 `grades.csv` 的汇总

## Constraints

### 真相归属：纯镜像，csv 说了算

同步按「课程 + 邮箱」**整行覆盖**，含回复状态。页面完全只读。想改回复状态要回
`ai-course` 仓库改 csv 再同步。

理由：`grades.csv` 由 `grade-homework.skill` 生成且人工在维护（实测值 `待回复`、`草稿已创建`）。
两边都能写就会分叉，而分叉一旦发生，没有任何一边有资格当准。§4.3 也明写这条链路要保留。

### 课程映射由人指定，系统不猜

CLI 形如 `sync --course S1 <path/to/grades.csv>`，课程走**现有 `course_aliases`** 解析
（与 `tools/course-import`、`tools/enrollment-backfill` 同一条路径）。

理由：上面已经实证目录名会错。而且这是 CLAUDE.md 记过的那条 ——「设计稿里的示例值不是
真实约束」的同类：**能让人指定的就别让代码猜**。

### 分项评分存有序数组，不存 JSON 对象

```
scores  jsonb   [{"item": "A1工作流结构", "score": 11}, …]
```

Postgres 的 `jsonb` **不保证对象键顺序**（按键长度+字节序重排）。而分项列的顺序是评分表的
一部分（A 工作流 / B 提示词 / C 输出 / D 心得 是分组）。存成对象出来就乱了。

### 架构纪律（既有，不重复论证）

浏览器 → Next.js → FastAPI → Postgres。CLI 走 FastAPI 的 HTTP 接口写入，不直连库。
migration 只进 `supabase/migrations/*.sql`。

### 隐私

真实学员姓名与邮箱不得进仓库，含测试夹具。测试数据一律虚构姓名 + `@example.com`。
CLI 的 dry-run 输出会打真实姓名 —— 它只在本地跑，但**不得整行 dump**，且要按
`enrollment-backfill` 那条教训用 `sys.stdout.buffer.write(...encode("utf-8"))`
（Windows 控制台 cp1252 会在第一行中文就抛 `UnicodeEncodeError`）。

## Success Criteria

### 数据层

1. 同一份 `grades.csv` 连跑两遍，第二遍新增 0 行、更新 N 行，总行数不变
2. csv 里某人的分数改了再同步，库里跟着改；csv 里的行删了**不**影响库（覆盖式，不是同步式删除）
3. 邮箱不在 `students` 表里的行被跳过，且在输出末尾被逐条列出（数量 + 邮箱），
   不静默丢弃、不中止整份导入
3b. 邮箱在 `students` 表里、但该课**没有报课记录**的行**照常写入**成绩，并在输出末尾
    **另起一份清单**列出。两份清单不得混在一起 —— 前者要先建学员，后者要补报课，处置相反
4. 总分存的是 csv 里那个数 —— 用 `session2` 那行「总分 ≠ 分项之和」的记录验证
5. 三份不同课程的 csv 都能导入，`scores` 里的 item 名与顺序与源文件表头逐一相同，
   且**没有为此改过任何表结构**

### 页面

6. `/homework` 选一门课，列出该课**在读学员**的报课记录（已归档学员不在名单里），
   每人一个状态：

   | 状态 | 判据 |
   |---|---|
   | 已交 | 有该课的提交记录 |
   | 未交 | 无提交 **且** 他的场次已结束 |
   | 未开放 | 无提交 **且** 他的场次尚未结束 |
   | 未定场次 | 无提交 **且** 报课记录没有场次 |

   「场次已结束」SHALL 复用后端既有的 `derive_session_state`（`course-scheduling-fields`
   引入、`enrollment-core` 已在用），不得另写一套日期比较。同一个概念两处实现会在
   `state_override`（人工把一场标成已取消）这类边界上分叉。

6b. 已归档学员**不进任何计数**（应交 / 已交 / 未交 / 待回复），但他的成绩记录仍在库里，
    从学员详情能查到。**这与报课页有意不同** —— 那边归档不影响计数，因为那是历史统计；
    这里的未交计数直接导向"催谁"，催已归档的人是错的

7. 筛选「全部 / 已交 / 未交 / 待回复」，各带计数。「待回复」= 已交且 `回复状态 != "已回复"`
8. 选中一个人，看到：总分、**本课排名**（第 N / M，按总分）、各分项的原始分、
   亮点、改进建议、回复状态、来源（`session1/grades.csv` 第几行）
9. 页面上**没有任何**修改、删除、同步按钮
10. 一门课一条提交都没有时，给出说明文字，而不是空表格

### 生产验收

11. 三份 csv 导入生产后，`/homework` 的「已交」计数为 S1 = **17**、S2 = 9、S3 = 1
    （不是 18 —— 见下一条，18 是行数不是人数）。
    ⚠️ **验收分两步**（见「已定的判断」第 5 条）：名单来自报课记录，而生产上报课是
    S1 = 14 / S2 = 8，比成绩人数少。先按同步输出的第二份清单补齐报课记录，
    这条才可能达标 —— 否则页面只会显示 14 / 8，而那是**正确行为**，不是缺陷。
12. S1 里那位交了两次的学员（18 行 / 17 人）只出现一次，且是后一次的成绩
13. 未交 / 未定场次的人数与报课页对得上

## User Stories

- 作为讲师，我想在一个地方看到某门课谁交了谁没交 —— 现在这个答案只存在于我自己脑子里
  和另一个仓库的 csv 里
- 作为讲师，我想看到某人这门课的分项得分和我当时写的改进建议，而不用回去翻 csv
- 作为讲师，我想知道「这门课还有几个人没交」，因为那就是我下一步要催的人
- 作为讲师，我改了 csv 里的成绩之后，希望重跑一次同步就好，不用担心跑重了会多出记录

## 已定的判断（起草时不确定，2026-07-31 与用户逐条确认）

1. **「未开放」按学员自己那一场算，不按课程整体。**
   他报课记录上的场次已结束 → 未交；场次在未来 → 未开放。
   稿子用的是课程级布尔（这门课开过没）。差别是实的：S1 已开过几场、又排了一场未来的，
   报了未来那场的人在课程级口径下会落进未交名单，**被误催**。

2. **已归档学员不进「应交 / 未交」统计，但选中时成绩仍可查。**
   这里**有意不照抄**报课页的先例（「归档不影响报课计数」，2026-07-30 拍板）：
   报课计数是历史事实的统计，而这里的未交计数**直接导向催谁**，催一个已归档的人是错的。
   同一个词在两页含义不同，所以口径也不同。

3. **同一课程同一学员在 csv 里出现两次时，取提交时间较晚的那一行。**
   提交时间相同则取文件里靠后的那一行。`session1` 确实有这种（18 行 / 17 人）。

4. **回复状态原样存、原样显示，不归一化。**
   csv 里实测出现过 `待回复`、`草稿已创建`；稿子用的是 `已回复 / 草稿待发 / 未回复`，
   两套词不一样，而纯镜像的逻辑推论是以 csv 为准。
   因此筛选项「待回复」定义为 **`回复状态 != "已回复"`** —— 注意 csv 里目前
   **一个 `已回复` 都还没出现过**，所以这个筛选今天等于"所有已交的人"。这是正确的，
   不是缺陷：讲师确实还没回复过任何一份。

5. **有成绩但没有报课记录的人：同步照常写入成绩，并在输出末尾单独列出，由人去补报课。**
   （自查时发现的洞）名单来自报课记录，而同步只检查「邮箱在不在 `students` 表」。
   「在学员表 + 有提交 + 无报课」的人，成绩进了库、页面上却一行不出现。
   生产上现有报课 S1 = 14 / S2 = 8，而成绩是 17 人 / 9 人 —— **差额不是零**。

   处置与「不在学员表」一致（跳过并列出），但**两份清单要分开列**，因为处置不同：
   前者要先建学员，后者要补报课。补报课这件事已经有 `enrollment-backfill` 在做，
   同步不该长出第二套建报课逻辑。

   ⚠️ 推论：**验收分两步** —— 先补齐报课记录，SC11 的计数才可能达标。

6. **CLI 独立成 `tools/homework-sync/`，不并进 `tools/enrollment-backfill/`。**
   backfill 是一次性的历史倒推（已归档），homework-sync 要长期反复跑。
   代价是 csv 解析逻辑有两份 —— 接受，因为两者读的列不同（前者只要邮箱，后者要整行）。

## 已知会踩的坑（来自 CLAUDE.md，实现时对照）

- `jsonb` 不保键序 —— 已在 Constraints 里处理成数组
- 清表 fixture 要跟着外键长：新增 `homework_submissions` 后，`empty_course_tables`
  之类的 fixture 要把它排在被引用方之前删，否则会让一批不相干的测试红在 setup 阶段
- 读接口没有 `ORDER BY` 时「第一条」不可依赖 —— 排名要显式排序，且排序键要能打破并列
- 表格外框的 `overflow-hidden`（为圆角）配可压缩 flex 子项会**静默裁掉**内容且没有滚动条 ——
  S1 有 18 行，够撞上；jsdom 量不出来，必须在真实浏览器里用足量数据验一次
- 命令行脚本输出中文要显式 UTF-8 写 stdout
- 每次请求的 SQL 往返次数要钉成断言（`test_query_roundtrips.py`）—— 新接口一并加
