22 条全是「未定场次」，这是倒推的必然结果——作业成绩说不出他上的是哪一场。 所以未定场次的呈现不是边缘情况，而是这一页的主要内容：要能一眼扫到。

「来源」这一列这次才有意义：三种值同时存在时它才是信息。 倒推 = 从作业成绩推出来的占位，日期也是推的；手工补录 = 人特意录的。

学员详情：每条报课多了两个动作

从零开始用 Claude 和 Cowork · 未定场次 · 报名于 2026-06-07 改场次删除报名
为什么必须有「改场次」：想给这个人补一条带场次的记录时，若走「补录」而不是「改」， 唯一索引不会拦（场次不同即合法），结果同一人同一门课两条 —— 一条未定场次、一条有场次。那不是重听，是重复。

课程页：不要把这个误读成"导入失败了"

从零开始用 Claude 和 Cowork
每场时长 150 分钟　·　场次 3 场　·　另有 14 人未定场次
第 1 场　2026-06-07（不显示已报人数）
倒推进来的 22 条全部未定场次，因此每一场的已报人数都是 0，而 0 不显示—— 课程页上看不到任何"已报 N 人"。信息全在课程层那句「另有 14 人未定场次」上。 这是设计如此，不是导入没成功。生产验收要专门确认这一点， 否则最可能的误判就是"跑完了但页面没变化"。

移动端

桌面单一视口，没有移动版 —— 与既有各页一致，这是既定的范围限定 （内部工具，讲师在电脑上用）。总表沿用学员名单那套表格骨架，窄屏下的表现与它相同， 本片不为此新增断点。

验收时最容易漏的两条

1. 占位页测试会变红，那是预期的。 app/(app)/placeholder-routes.test.tsx 断言「报课渲染其占位页」—— 这一片正是要把它换掉。红的时候要认出这是计划内的，别当成缺陷去查。

2. 重跑幂等要真的跑第二遍。 代码里有 try/except ≠ 数据库真的挡住了 —— NULL != NULL 那条坑的教训就是这两件事不是一回事。
