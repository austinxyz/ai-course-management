# 学员管理系统

北美华人 Claude AI 课程的学员档案、报课、作业与互动管理。供讲师与合作伙伴使用，不面向学员。

## 现状

**已上线**：https://ai-course-management.vercel.app/students

学员名单跑在 Vercel + Render 免费档 + Supabase 云库上（`student-management`、`deployment`、
`access-control`、`student-write` 四个 change，均于 2026-07-29 归档）。`git push main` 后代码由平台自动部署，
数据库 migration 由 GitHub Actions 自动推送。

**访问需要密码**——整站 HTTP Basic Auth，浏览器会弹凭据框（用户名任意，密码即 `SITE_PASSWORD`）。
你和合作伙伴共用同一个密码，**不做每人一个身份**：因此无法单独吊销某人，互动记录也无法区分是谁录的。
也**不做限流**——密码长度是唯一防线。

**学员档案的增删改已上线**：新增学员、逐字段编辑（含姓名）、打标签、归档与恢复，都真正写入数据库。
姓名可改这点是为导入数据准备的——Notion 那批记录里有人的"名字"其实是群昵称，
改不了就只能归档重建，而重建会把手写备注一起丢掉。**邮箱仍不可改**，它是主键。
**检索匹配姓名、邮箱、微信昵称、微信名、微信号**（任一命中，大小写不敏感，不含标签与备注）——
拿着微信群名单人工对齐时，昵称往往是手上唯一有的信息。
归档是软删除——记录与关联数据都保留，随时可恢复；**系统不提供硬删除**，真要删得直连数据库。
新增时若邮箱已存在，会区分对方是在读还是已归档给出不同提示，且**不会覆盖或自动恢复**已归档记录。

**课程与场次已上线**：建课（课程名、一句话定位、招生介绍、每场时长、作业题目、上架状态），
一门课下排多场，**每场自己的讲师**——报满后加的第二场、为亚洲时区加的晚场，往往不是同一个人。
场次时间**按你选的时区填**（美西 / 美东 / 加拿大 / 上海），标签跟着选中的时区走，
页面再给出其它时区对应时间 —— 讲师排美东晚 8:30 就直接填 20:30，不用先在脑子里换算。
跨夏令时也不会错一小时（存的是墙上时间与时区名，不是固定偏移）。
每门课可设一个默认时区，新增场次时预选它，但不影响已排好的场次。
每场时长以**分钟**计（真实课程是 150 分钟，整小时表达不了）。
场次状态默认跟着日期走，可人工改成已取消、也能恢复跟随。
课程可登记**平台别名**（`S1`、`Session 1`…），导入报课数据时按这些写法匹配到本课程。
课程没有删除，只有上架 / 已下线——它是报课、作业、催作业共用的口径。

**报课的数据主干已上线**：打开一名学员，在「报课记录」区块点「补录报课」就能记一条——
选课程、可选场次、报课日期、备注。**场次可以先不定**（平台数据常常不给，而"还没定上哪一场"
是一个需要跟进的真实状态）。

状态只存**报名**与**退课**两种，**「已完成」不入库**——它由那一场的日期算出来。
理由是没人会在每次课后回来把十几条记录挨个改成已完成，存下来的状态会腐烂。
场次被取消时算"报名"而不是"已完成"：课没上成，人还欠一场。
没上成想补后面那一场？**改这条报课的场次**即可，状态自己就回到报名——没有单独的状态开关，
因为那会让"这个人属于哪一场"出现两个互相矛盾的答案。

同一个人**重复听同一门课**是允许的（目前不额外收费），那是两条报课记录、各占一场的位子；
但**作业只算一份**，将来催作业按人去重，不会催她两遍。

课程页上，场次卡片显示「已报 N 人」，课程还会显示「另有 N 人未定场次」——
后者不另计的话，那批人在这一页上完全不可见，而他们恰恰是需要你去指派的。
**两个数字为 0 时都不显示**：一门课刚排好场次还没招生时，满屏的「已报 0 人」比留空更吵。
归档一名学员**不改变**任何计数——归档说的是"他还在不在名单里"，报课说的是"他报没报这门课"；
人真的不来了，正确的表达是把那条报课标退课。
**删除有报课记录的场次会被拒绝**并告诉你有几条挡着，得先把这些人改派或清空场次。

`/enroll` 是**只读的报课总表**：一眼看到全部报课，可按课程筛选，未定场次的人一扫就见。
改动不在这里做——写入只在学员详情一处，避免同一件事有两条写入路径。
每条报课都能**改场次（含清空）或删除**：删除是给录错的记录用的，退课表示"这件事发生过"，两者不同。

**历史报课已经倒推进来了**：一个学员如果有某门课的作业成绩，他必然报过那门课。
据此从 `grades.csv` 建了 22 条（S1 14 人、S2 8 人），**全部未定场次**——
作业成绩说不出他上的是哪一场，这正是需要你去指派的那批人。
它们的来源标为**倒推**，与你手工补录的记录区分开：将来平台数据接上时，
倒推的占位**可以**被覆盖，你手工录的**不会**。

批量导入（CSV / 手工粘贴 / 平台 API）与待处理队列归下一片（`enrollment-import`），
阻塞于 EliteCoach101 的导出方式未定。

**作业已上线**：`/homework` 是 `ai-course/tools/homework-grader/session*/grades.csv` 的
镜像，权威副本始终是那份文件——页面上不提供逐条改分数的入口，改分要回源文件改，
再从网页把新文件导进来。按课程看名单，每人一个状态：

| 状态 | 含义 |
|---|---|
| 已交 | 有这门课的提交记录 |
| 未交 | 报了课、场次已结束、没交 —— 这批就是要催的人 |
| 未开放 | 报的那一场还没上，现在没交是正常的 |
| 未定场次 | 报课上还没指派场次，所以谈不上交没交 |

三种"没交"用三种颜色，因为它们要你做的事完全不同。
「未开放」按**学员自己报的那一场**判定，不按课程整体——否则报了未来场次的人会被误催。
选中一个人能看到总分、本课名次、各分项的**原始分**、亮点、改进建议，
以及这条记录来自哪个文件的第几行。

分项列各课完全不同（S1 是 A1–D2 共 10 项，S2 是 E1–G2 共 9 项，无一相同），
整列原样存下，**新增一门课不需要改数据库结构**。总分取源文件里那个数、**不重算**——
真实数据里就有一行总分与分项之和对不上，镜像的职责是忠实而不是纠正。
已归档与已退课的人不进名单，因为这里的计数直接导向"催谁"（这一点与报课页**有意不同**，
那边的已报人数是历史统计）。

**导入从网页做**：作业页的「导入 grades.csv」选一个文件，先看一屏预览
（按什么编码读的、将新建/将更新多少条），确认了才写。
业务逻辑全在 `POST /api/homework/import`，网页只负责把**原始字节**转发过去——
下一个调用方是批改 skill 的 MCP，它不经过 Next.js。
原来的本地命令行 `tools/homework-sync/` 已随 `homework-upload` 删除。
邮箱不在学员表的行不再跳过：系统自动建一条最小学员档案（区域/基础/来源用占位值，
姓名从源文件取、缺失则写「待定」）与一条报课记录，成绩正常写入，预览里显示为
「自动建档」；讲师之后自行去学员页回填真实信息。已在册但没报这门课的人另算一份
「无报课记录」清单——成绩写了，只是不出现在作业页名单上，需要补一条报课。
系统还维护一份**排除名单**（全课程通用，键是邮箱）：讲师本人在 `grades.csv` 里的测试提交
永远不会被当成真实成绩导入，预览里会显示为已排除；也能在预览的任意一行上把某个邮箱
永久加入这份名单。

讲师实际回复学员往往在系统之外（私信、邮件）发生，`grades.csv` 原文那一列常常没跟上，
所以详情面板有一个独立的**讲师标记**——可以来回切换「已回复 / 未回复」，标记不受
重新导入影响。名单表格的「回复」那一列与「待回复」筛选都**以这个标记为准**，
不看源文件原文。

**批改流程产出的详细报告可以逐条上传**：详情面板选中一条提交后，「上传批改报告」
一个按钮弹出系统文件选择框选 `.md` 文件。上传后先预览——逐分项评语（每条带勾选框，
默认全部勾选）、整体的亮点/改进建议，得分与现有记录不一致的分项标黄警告但**不阻止
确认**；确认后勾选的分项评语挂到对应分项行下面，亮点/改进建议被报告覆盖并标注
「来自批改报告」来源徽章。这两个字段一旦被报告覆盖过就**锁定**：之后这门课重新导入
`grades.csv` 不会再把它们冲回精简版，其余字段（总分、分项分、回复状态原文等）
照常整行更新。
各分项的**满分**不在 `grades.csv` 里（在另一个仓库的 `rubric.md`，且那份文件对过错，
不可信），所以满分改成课程页手动维护：讲师在课程页给某门课的各分项填一个满分，
分项名字系统自动从已导入成绩里去重列出，不用手打。配了满分之后，分项显示
`11 / 15` 并配一条按比例条形图，条形图与分数按同一套三档阈值染色（≥90% 绿、
70%–90% 黄、<70% 红）；总分只在**这条提交全部分项都配了满分**时才显示进度条+颜色。
名单表格每行还有一串迷你竖条（每个分项一根柱子），不点进详情就能看出弱项在哪。
没配满分的分项照常只显示原始分，不阻塞使用。

**催作业 MVP 已上线**：`/nudge` 按课程展示"已报课但未交作业"的名单（复用 `/homework` 页
的"未交"判定），每人带逾期天数（距所报场次上课日期）、已催次数、上次催促时间。选中一人，
系统自动起草一份套好姓名/课程/逾期天数的催促文案，讲师可以直接改。这一版**不接真实发信通道**
（不接 Gmail、不接微信自动发送）——讲师看好文案后自己复制发送，发完点"标记已催"系统记一条
互动事件；也可以"跳过"某条未交（从名单排除，直到这条未交状态重新出现）。侧边栏"催作业"
数字是全课程合计的待催人数。

多套文案语气切换、导出名单、批量发送、真实发信通道、完整的互动记录能力（人工录入 1:1 沟通、
参与度信号导入）都还没做。

> **护栏已于 2026-07-29 解除**，生产库开始存放真实学员数据。
> 这是在访问控制上线并通过写入验收之后做出的单独决定，不是随认证自动失效的。
>
> 仍然有效的是另一条：**仓库里不得出现任何真实学员数据**，包括测试夹具。
> 测试数据一律用明显虚构的姓名与 `@example.com` 邮箱。
> `supabase/seed.sql` 是本地专用文件，`supabase db push` 不会推送它——生产库的内容只来自界面录入与后续导入。

> 后端跑在 Render 免费档，15 分钟无请求会休眠。冷启动约需 1 分钟，
> 期间页面会显示"暂时无法加载"并提供重试按钮——这是预期行为，不是故障。

本地跑起来见 [docs/setup.md](docs/setup.md)。

## 要解决什么

现有的 Notion 方案（Phase 1）能存作业成绩，但：

- **没有报课数据** → 算不出"谁该交作业但没交"
- **微信字段全空** → 催作业时拿不到联系方式
- **不适合批量运算** → 算名单、批量起草邮件都要反复调 API

核心目标是让**催作业自动化**：算出未交名单 → 起草个性化文案 → 发邮件 → 记录已催。

## 技术栈

```
浏览器 → Next.js 15 (App Router) → FastAPI (Python 3.12) → Supabase 托管 Postgres
```

浏览器不直连后端，也不直连数据库。详见 [CLAUDE.md](CLAUDE.md) 的架构纪律。

## 开发流程

走 opsx 四阶段：`explore → propose → apply → archive`。

## 隐私

本系统处理真实学员个人信息。仓库不提交任何真实学员数据，测试一律使用虚构姓名与 `@example.com` 邮箱。
